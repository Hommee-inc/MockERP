# MockERP v0.5 — Cenários de Erro Controlado (Guia)

## O que você vai aprender

Como introduzir problemas de forma parametrizável e documentada, em vez de gerar dado ruim por acidente (que é o que você evitou nas versões anteriores).

## Conceitos para pesquisar antes de começar

- A diferença entre um bug (dado ruim sem querer) e uma anomalia controlada (dado ruim de propósito, documentado)
- Por que um "gabarito" de anomalias injetadas é importante: sem ele, ninguém consegue medir se o pipeline de qualidade (v1.1) realmente pegou o que deveria

## Catálogo de anomalias para implementar

Organize seu código de forma que cada anomalia possa ser ligada ou desligada de forma independente:

- Duplicidade: cliente duplicado, venda duplicada
- Inconsistência: venda sem movimento de estoque, estoque negativo, conta a receber com valor diferente da venda
- Registro faltante: devolução sem item de venda de origem, pagamento sem conta a receber
- Relacionamento inválido: venda referenciando cliente que não existe
- Alteração de estrutura: uma nova versão de uma entidade com um campo a mais
- Divergência entre documentos: valor do orçamento diferente do valor da venda convertida

## Passo a passo sugerido

1. Não misture a lógica de anomalia dentro dos geradores da v0.1 a v0.4. Escreva uma camada separada, que recebe o dataset golden (v0.4) já pronto e aplica as anomalias por cima
2. Para cada anomalia aplicada, registre num arquivo separado (o "gabarito") qual registro foi afetado e que tipo de problema foi introduzido nele
3. Deixe as taxas de cada anomalia configuráveis (por exemplo, num arquivo YAML), em vez de fixas no código

## Ponto de atenção

Pense por que essa separação (gerar limpo primeiro, sujar depois) é melhor do que gerar tudo já sujo de uma vez. Uma pista: se a lógica de anomalia estivesse misturada dentro do gerador de venda, como você faria para gerar, uma vez, um dataset 100% limpo para comparar?

## Como saber se está certo

Gere o dataset com anomalias e depois confira, manualmente, se cada linha do gabarito realmente corresponde a um problema real no dataset gerado. Esse é o teste mais importante desta versão: o gabarito precisa ser confiável, porque ele vai ser usado na v1.1 para medir se a camada de qualidade realmente funciona.

## Ângulo do post

MockERP v0.5: agora o MockERP sabe gerar problema de propósito. Duplicidade, relacionamento inválido, divergência entre documentos, tudo configurável e documentado, prontos para quem quiser praticar detecção e tratamento de dados ruins.
