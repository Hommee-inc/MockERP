# MockERP v1.3 — Plataforma Databricks: Avançado (Guia)

Essa versão tem vários conceitos novos e relativamente avançados. Não tente implementar todos ao mesmo tempo, vá um de cada vez, confirmando que cada um funciona isoladamente antes do próximo.

## O que você vai aprender

Ingestão incremental, o que muda quando o schema de uma tabela evolui, como fazer upsert de forma idempotente, como manter histórico de mudanças, e como orquestrar tudo isso como um pipeline único.

## Conceitos para pesquisar antes de começar

- Auto Loader no Databricks: o que ele resolve que a leitura batch simples (v1.0) não resolve
- Schema evolution: o que acontece, por padrão, quando um arquivo novo chega com uma coluna que a tabela Delta não tem
- `MERGE INTO` em Delta Lake (o comando por trás do upsert), e por que ele evita duplicar dados quando você reprocessa a mesma entrada duas vezes
- SCD Type 2 (Slowly Changing Dimension tipo 2): o conceito de manter histórico de um cadastro que muda ao longo do tempo, usando `valid_from`, `valid_to` e `is_current`
- Databricks Jobs/Workflows: como encadear notebooks com dependência entre eles

## Passo a passo sugerido

1. Substitua a leitura batch da v1.0 por Auto Loader na ingestão da Bronze
2. Gere uma segunda versão de uma das entidades (por exemplo, `sales` com uma coluna nova, `sales_channel`) e rode a ingestão de novo, observando o que acontece com o schema da tabela
3. Implemente `MERGE INTO` para atualizar o cadastro de clientes, em vez de sempre inserir tudo de novo
4. A partir do merge, implemente SCD Type 2 só para o campo que pode mudar (por exemplo, se você tiver um limite de crédito por cliente), preservando o valor anterior com uma data de validade
5. Crie um Job no Databricks que executa, em ordem: geração de dados, ingestão Bronze, transformação Silver, construção Gold
6. Simule uma falha de propósito (por exemplo, um arquivo com um valor de data inválido) e documente o que acontece com a execução do Job quando isso ocorre

## Ponto de atenção

Ao testar schema evolution, rode a ingestão duas vezes, uma vez com o schema antigo, outra com o novo, e observe atentamente a mensagem que o Databricks mostra na segunda execução. É mais valioso entender essa mensagem do que decorar o comando.

## Como saber se está certo

Você deve conseguir mostrar, com prints reais: a tabela ganhando uma coluna nova sem quebrar, uma execução do merge que não duplica registros mesmo rodando duas vezes seguidas, um registro de cliente com duas linhas de histórico (uma antiga, uma atual) e uma execução do Job que falhou de propósito, seguida de uma que corrigiu e teve sucesso.
