# MockERP — Project Guidelines

## Platform limitations

The target environment is Databricks Free Edition. The project must separate
software-engineering standards from capabilities that depend on a workspace.

- The Python package must not depend on paid Databricks features.
- Jobs, compute, Unity Catalog, Volumes, networking, and package installation
  must be validated before use.
- Free Edition limitations must be documented as execution limitations, never
  hidden inside generator logic.
- Domain code must remain locally testable when execution or persistence
  depends on Databricks.

## Language rule

All repository artifacts must be written in English: source code, comments,
docstrings, documentation, tests, notebooks, schemas, labels, and commit
messages. Requests may use another language, but implementation output must be
English.

## Goal

MockERP must generate a simulated ERP, not merely a collection of random
values. Every record needs context, identity, relationships, and verifiable
business rules.

## Core principle

```text
Faker generates values
Provider adapts values
Generator creates entities
Orchestrator respects dependencies
Tests prove consistency
Databricks executes and stores data
```

If two tables are generated without an explicit relationship, the result is a
data collection, not an ERP mock.

## Generator configuration

Every `generate_*` function must receive a configuration object or dictionary.
Use one shared configuration contract across the generation pipeline:

```python
config = {
    "locale": "pt_BR",
    "seed": 42,
    "data_quality_mode": "clean",
}
```

Use `data_quality_mode` rather than an ambiguous flag such as `dirt`:

- `clean` preserves guardrails and business invariants;
- `dirty` explicitly enables configured invalid or duplicate data for payload
  and ETL tests.

Dirty mode must not disable every validation implicitly. Each relaxed rule must
be explicit, documented, and covered by a test. Clean mode is the default.

## Mandatory rules

### 1. Entities have their own identity

Every entity must have a stable and unique identifier within the dataset:

- `customer_id` for customers;
- `product_id` for products;
- `budget_id` for budgets;
- `sale_id` for sales;
- `return_id` for returns.

IDs must not be names, accidental indexes, or values generated by Faker.

### 1.1 Business identifiers are validated separately

CPF and CNPJ are not primary keys, but they are unique business identifiers in
the clean golden dataset. The entity generator must prevent duplicate
identifications during normal generation.

Duplicate CPF/CNPJ values are useful for ETL and data-quality exercises, so the
system must support them through an explicit anomaly or duplicate-injection
mode. They must never appear accidentally in the default clean scenario.

### 2. Relationships are created at the source

A dependent entity must receive the valid entity or IDs it depends on:

```text
Customer
  └── Budget.customer_id
      └── Sale.budget_id + Sale.customer_id
          └── Return.sale_id
```

Do not generate sales and customers independently and then randomly choose IDs.

### 3. Business rules belong in generators

Providers generate individual values. Generators define domain rules:

- a sale can only originate from a converted budget;
- a sale preserves the customer and items from its budget;
- a return references an existing sale;
- returned quantity cannot exceed sold quantity;
- derived values are calculated from source documents.

### 4. Generation order represents the domain

The flow must follow real dependencies:

```text
customers/products
      ↓
budgets + items
      ↓
sales + items
      ↓
returns + items
      ↓
inventory and finance
```

The code should make this order visible, keeping dependent-entity creation near
the decision that creates it.

### 5. Derived data is not randomly generated again

When a value already exists in a source entity, dependent values must be copied
or calculated:

- `Sale.customer_id` comes from the budget;
- `Sale.total_amount` comes from sale items;
- inventory output comes from sold quantities;
- accounts receivable come from sale values;
- refunds come from return values.

Randomly generating these values again creates accidental inconsistency.

### 6. Randomness must be reproducible

Generators must accept a seed. The same scenario and seed must reproduce the
same dataset for debugging, tests, and layer comparisons.

### 7. Providers do not know the ERP

`FakerProvider` may generate a CPF, name, or address, but it must not decide
whether a sale is approved or a return is valid. Those decisions belong to
generators and domain rules.

### 8. Notebooks are entry points

Databricks notebooks and Jobs configure parameters, call the package, display
results, and persist data. They must not duplicate providers, generators, or
relationship rules.

### 9. Anomalies are a separate layer

Through v0.4, the golden dataset must remain consistent. Starting with v0.5,
anomalies must be applied by an explicit layer over the clean dataset.

```text
consistent golden dataset
          ↓
configured anomaly
          ↓
training dataset with a known issue
```

### 10. Every generator needs tested invariants

Tests must verify relationships, not only that functions execute:

- every foreign key points to an existing record;
- totals equal the sum of items;
- dates respect event order;
- statuses are allowed;
- quantities and values follow domain rules.

## Implementation conventions

- Reusable code belongs in `src/mockerp/`.
- Contracts belong in `providers/provider_contract.py`.
- Library adapters belong in `providers/`.
- Entity rules belong in `generators/`.
- Databricks orchestration belongs in `notebooks/` or Jobs.
- External dependencies belong in `pyproject.toml`.
- Every new entity must include a generator, tests, and relationship
  documentation.

## New-entity checklist

- What is the primary key?
- Which entities does it depend on?
- Which foreign keys does it carry?
- Which values are derived and which are independent?
- What is the correct creation order?
- Which invariants must always be true?
- How will the entity be used in future roadmap versions?
- Is there a test proving that it is not just an independent table?
